Checklist operations

Find the correct shift, record truthful outcomes, and leave a usable handover.

Access: Checklist operations access; available actions also depend on your role, participation and the run state.

Navigate to /checklists

Find a shift or historical run

Before you begin: Know the operating date and shift.

  1. Set the time window

    Open Checklists. Choose All Time, Week, Specific Day or Date Range, then use search, lifecycle and shift filters.

  2. Open the matching run

    Check its date, shift hours and lifecycle before opening. Today coverage describes initialization, not completed work.

Confirm success: The workspace header matches the intended shift and date.

Stop and check: Do not work in a historical or completed run simply because its title matches today.

Work an item and its substeps

Before you begin: Open the intended run and join if participating.

  1. Read before acting

    Read the item instructions, type, timing and existing activity. Start Working where offered; this claims progress, not completion.

  2. Record the actual outcome

    Open substeps for multi-step work. Mark Complete only after checking the real system. Skip or Report Issue requires the reason/evidence requested by the dialog. Use Previous, Next and Next Open to navigate; navigation does not record an outcome.

  3. Verify the saved state

    Wait for the response. Check the item/subitem state and progress. Expand activity to inspect who recorded the result and when.

Confirm success: Each action is reflected in the saved status and activity.

Stop and check: If a save fails, refresh and inspect the recorded state before repeating it. Do not mark unfinished work complete to reach 100%.

Coordinate members and handover

Before you begin: Join the shift when doing work; know what the next operator needs.

  1. Review incoming notes

    Open Handover notes, filter Incoming and read priority, context and required follow-up. Acknowledge only after reading; acknowledgement is not resolution.

  2. Leave a useful note

    Choose Add Handover Note. Describe what happened, what is pending, the affected service/reference and the next action. Select the available priority/destination fields and save.

  3. Confirm team context

    Check Team members and participation. Presence is connection/activity context, not proof that someone completed an item. Filter Outgoing to confirm your saved note.

Confirm success: The next shift can see the note and its acknowledgement state.

Stop and check: Do not put passwords or unnecessary customer details in notes.

Close, inspect, share or export a run

Before you begin: Review incomplete items, exceptions and handover first.

  1. Resolve outstanding work

    Use the open-item view to find gaps. Normal completion and exception completion are different outcomes; supply the required justification for exceptions.

  2. Finalize once

    Use the completion control available to your role and state, review the confirmation, then verify the saved lifecycle. Inspect opens the record for review.

  3. Share the evidence

    Use Share for the run link or PDF for a snapshot. Recipients still need access to open the live record; a PDF will not update after download.

Confirm success: The final lifecycle and exported snapshot tell the same story.

Stop and check: A closed shift can still have exceptions. A completed counter alone is not evidence of a clean close.

Troubleshooting

No runs match

Clear filters and check the date and shift. If coverage was not initialized, contact the planner; do not invent a replacement record.

Action unavailable

Check participation, lifecycle and role. Ask the owner/admin about missing authority.

Terms

Lifecycle: The state of the whole checklist run.

Subitem: A smaller executable step within an item.

Template authoring

Build reusable shift instructions and review them before operators use them.

Access: Template authoring access and the role required by the create/edit/delete controls.

Navigate to /templates

Create or revise a template

Before you begin: Know the section, shift and operating procedure.

  1. Choose the template

    Open Templates from Checklists or the command menu. Inspect an existing template before creating a duplicate. Choose Create or Edit as appropriate.

  2. Build the work in order

    Set the required template fields. Add ordered items and subitems with clear instructions, types and timing. For conditional/scheduled work, fill the fields the builder exposes and check the condition or schedule rather than assuming it applies every day.

  3. Save and inspect

    Resolve validation errors, save, then open View to verify the resulting briefing and item order. Template edits define future work; review a live run separately.

Confirm success: The saved template has the correct shift, instructions and sequence.

Stop and check: Do not use template edits as a way to alter the history of an already executed run.

Review or retire a template

Before you begin: Confirm the template identity and operational owner.

  1. Inspect the briefing

    Use View to check every item, subitem, timing and required action. Compare it with the approved operational procedure.

  2. Edit or delete deliberately

    Edit to correct instructions. If Delete is available, review the confirmation and impact before accepting; do not remove a template still required for shift coverage.

Confirm success: The library shows the intended current template.

Stop and check: If unsure whether a template is still used, stop and confirm with the shift owner.

Troubleshooting

Validation fails

Correct the named field or item in the builder, then save again.

Missing control

Template entitlement does not override role restrictions.

Terms

Template: The reusable blueprint; an instance is a dated run created from it.

Task workspace and analytics

Keep persistent work owned, dated and traceable beyond a shift.

Access: Task workspace access; editing and assignment depend on your role and relationship to the task.

Navigate to /tasks

Find and investigate work

Before you begin: Know whether you own, assigned or supervise the work.

  1. Choose a lane

    Open Task Center. Choose Assigned To Me, Tasks I Assigned, Team Tasks, Overdue or Completed as appropriate.

  2. Narrow and inspect

    Search and filter status/priority. Open the task details; read description, assignee, due date, comments and history before changing anything.

Confirm success: You can identify the owner, next action and latest recorded change.

Stop and check: A completed task may have been completed late; retain that distinction.

Create, assign and update a task

Before you begin: Have a clear outcome, owner and realistic due date.

  1. Create the work

    Use the create task action. Fill the required title, description, scope/type, priority, assignee and due date fields offered by the form.

  2. Progress the task

    Open details or Edit. Update the permitted fields/status and record useful context in comments. Save and wait for confirmation.

  3. Verify and close

    Complete only after verifying the outcome. Reopen/edit only where permitted, and check history after changes. Read analytics in the context of the selected scope.

Confirm success: The task card and history reflect the saved owner, dates and outcome.

Stop and check: Do not delete or mark work completed to conceal a missed deadline.

Troubleshooting

Task missing

Check lane, filters and permissions before recreating it.

Save failed

Reopen the task and check history before retrying.

Terms

Overdue: The due time has passed without the required completion.

Database growth and capacity

Read capacity, growth and estimated runway without changing the database.

Access: Database growth and capacity access; this screen is telemetry and forecasting.

Navigate to /database-stats

Assess current capacity

Before you begin: Know which database the configured telemetry describes.

  1. Check freshness

    Open Database Statistics. Read the timestamp and connection/cached-fallback state before using the figures. Refresh if needed.

  2. Compare capacity and growth

    Read used space, provisioned total and remaining buffer. Inspect Growth contour and Daily ledger for actual changes rather than relying on one value.

  3. Interpret runway

    Read the estimated full date, risk state and confidence/control notes. Compare current daily growth with the seven-day average; escalate sustained pressure with the timestamp and evidence.

Confirm success: You have a dated capacity assessment, with uncertainty explained.

Stop and check: A forecast is an estimate, not a guarantee or a command to expand/shrink storage.

Troubleshooting

No or stale telemetry

Refresh once; if still stale, escalate the source connection and include the last successful timestamp.

Terms

Runway: Estimated time until available capacity is consumed at the observed growth rate.

Cached fallback: Previously fetched evidence used when fresh telemetry is unavailable.

Performance and achievements

Understand recorded contribution, evidence-based reliability and achievement levels.

Access: Performance access; the screen uses the visible person/team scope.

Navigate to /performance

Understand a score fairly

Before you begin: Choose the period you want to review.

  1. Read Overview

    Check contribution points separately from reliability rates. A dash means no eligible evidence; a limited sample needs more observations.

  2. Inspect Evidence & scoring

    Read the breakdown, eligible samples, weights and recent contributions. Tasks without deadlines can earn completion credit without a timeliness bonus. Passive membership and days off are not contribution evidence.

  3. Interpret team context

    Compare recorded contribution volume with workload and shift opportunities. Shared ranks can occur for ties; the table is not a staff appraisal.

Confirm success: You can explain the score using underlying records and sample sizes.

Stop and check: Do not infer poor performance from missing evidence or compare different workloads as equivalent.

Earn and collect achievement levels

Before you begin: Open Achievements and choose an award.

  1. Read the requirements

    Inspect Amateur, Skilled and Expert requirements and remaining progress. Every requirement for a level must be met.

  2. Collect in order

    Collect the available level when enabled. Verify it becomes collected before trying the next level. Current progress uses the calendar year; previously unlocked/collected levels remain recorded.

Confirm success: The achievement shows the earned level and the next requirements.

Stop and check: Do not create duplicate work or work unnecessary hours solely for points.

Troubleshooting

Unexpected score

Check the selected period and underlying completion/attendance records. Raise a specific record discrepancy with the administrator.

Terms

Contribution: Credit for recorded eligible work.

Reliability: A rate calculated from eligible evidence, not raw volume.

Team scheduling and patterns

Plan coverage using section-specific patterns, date ranges and individual assignments.

Access: Team scheduling access; the current Team page requires Admin or Manager.

Navigate to /team

Inspect coverage for a date or person

Before you begin: Select the correct section.

  1. Set the view window

    Use the shortcuts or custom date/range controls. Apply the member/user filter to inspect a specific person; clear it to review the section.

  2. Read the schedule

    Check shift dates, hours, coverage and assignments. Open an assignment for details before editing it.

Confirm success: The visible schedule matches your section, dates and people.

Stop and check: A filtered empty schedule does not prove the whole team has no assignments.

Create or maintain a shift pattern

Before you begin: Know the rotation, shift definitions and timezone.

  1. Open Patterns

    Create a pattern or edit the intended existing one in the selected section. Set name, rotation/cycle, shift sequence and any rest/off days shown by the form.

  2. Review and save

    Check ordering, hours and timezone. Save and verify the pattern appears in this section. Delete only an obsolete pattern after checking its use.

Confirm success: The pattern is available to Smart Assignment for the same section.

Stop and check: Do not invent shift times to work around a missing pattern; obtain the planner-approved definition.

Use Smart Assignment

Before you begin: Have a saved pattern or a known single shift and selected members.

  1. Choose the assignment mode

    Open Smart Assignment. Bulk Pattern needs a pattern and start/end dates. Single Shift needs a date and shift.

  2. Set the scope

    Choose the correct section pattern, dates and members. Check that the end is not before the start and that the selected people are intended.

  3. Assign and verify

    Submit once. Inspect the resulting schedule across the full requested range, not only the first day. Correct individual assignments using the provided edit/remove controls.

Confirm success: Members have the intended dates and shifts in the schedule.

Stop and check: If patterns fail to load, use Retry patterns. If none exist, create one in the current section first.

Troubleshooting

Wrong/missing pattern

Verify section selection, retry loading, then inspect Patterns.

Assignment conflict or rejected save

Read the server response and inspect existing assignments before resubmitting.

Terms

Pattern: A reusable rotation, applied over a date range.

Personal schedule

See your upcoming shifts and open the correct work for the day.

Access: Personal schedule access; this is your assigned schedule, not the planner.

Navigate to /schedule

Prepare for a shift

Before you begin: Check your signed-in identity.

  1. Choose the time view

    Open Schedule from the operator menu. Use its calendar/time controls to find the intended date.

  2. Inspect the assignment

    Read shift hours, section and relevant details. Open the linked checklist when offered and confirm its date before joining.

  3. Resolve a mismatch

    If an expected shift is absent or incorrect, contact the Team planner with the date and shift. Check again after correction.

Confirm success: You know when to work and which checklist belongs to that shift.

Stop and check: Do not assume a calendar entry alone proves attendance or completion.

Troubleshooting

No assignments

Check the date range and your account; ask the planner to verify section/member assignment.

Terms

Assignment: The shift allocated to you by the planner.

Service monitoring and investigation

Identify degraded services and inspect current signals before escalating.

Access: Service monitoring access; manual checks and controls additionally require configuration authority.

Navigate to /network-sentinel

Investigate a live service

Before you begin: Know the service, environment or affected group.

  1. Scope the service list

    Filter environment, service group, search and health. Read connection/freshness indicators before interpreting the counts.

  2. Inspect the signal

    Select the service. Read Signal for sampled availability and latency, and Evidence for the latest probe/reason. Compare ICMP and TCP evidence; a failed network probe is not proof that every business function has failed.

  3. Preserve evidence

    Use Evidence TXT to download a dated investigation snapshot. Include service/environment and timestamps when escalating.

Confirm success: The selected service has a clear, dated evidence trail.

Stop and check: Unknown or stale signal is not healthy. Do not infer recovery from an interrupted live connection.

Request a current check

Before you begin: The service must be selected; Check now must be available to your role.

  1. Check once

    Choose Check now and wait for the response. Read the separate manual-probe result and its timestamp.

  2. Compare observations

    Compare the manual result with scheduled monitoring and incident evidence. Refresh/reopen the service if needed before escalation.

Confirm success: The manual result identifies what was checked and when.

Stop and check: Repeated clicks do not make monitoring more reliable; investigate persistent failure instead.

Troubleshooting

Live updates interrupted

Keep the last snapshot marked stale, refresh and check the monitoring source connection.

Terms

ICMP: A network reachability probe, often called ping.

TCP: A connection check to a configured service port.

Sampled availability: Availability inferred from recorded probes, not continuous proof of business success.

Outage ledger and event history

Trace outages and major events for a selected service.

Access: Outage ledger access; service monitoring permission is separately required for Signal/Evidence.

Navigate to /network-sentinel

Trace an outage

Before you begin: Identify the service and approximate incident date.

  1. Open Timeline

    Select the service, then Timeline. Review current outages, today’s events and the Major Events Archive.

  2. Read the chronology

    Compare start/end times, duration, severity and summaries. A restored service and an unresolved investigation are different facts.

  3. Escalate with references

    Record service name, environment and event timestamps. Use the live investigation to confirm present health rather than treating historical recovery as current evidence.

Confirm success: You can describe the outage sequence and distinguish it from current health.

Stop and check: Only retained events are visible; no older rows does not prove there were no earlier outages.

Troubleshooting

Archive empty

Check the service and today’s events; older retained events appear separately.

Terms

Outage: A recorded period of detected service failure.

Service configuration and controls

Maintain monitoring targets and control whether checks run.

Access: Configuration access plus Manager/Admin for add/edit/check/enable; Delete requires Admin.

Navigate to /network-sentinel

Add or edit a monitored service

Before you begin: Obtain the approved target host, ports, environment and monitoring requirements.

  1. Open the editor

    Choose Add Service or select a service and Edit. Verify the service identity and environment before changing the target.

  2. Set the checks

    Fill the displayed address/port, probe and timing fields. Use appropriate target values; save and read any validation response.

  3. Verify monitoring

    Select the saved service, run Check now if allowed and inspect fresh evidence. Saving configuration is not proof of reachability.

Confirm success: The saved target and new probe evidence match the intended service.

Stop and check: Do not point production checks at a test host or use a successful ping as proof of application availability.

Enable, disable or remove monitoring

Before you begin: Know the maintenance/change reference and affected service.

  1. Choose the scope

    Select the exact service and read its identity. Disable pauses its monitoring; Enable resumes it.

  2. Confirm the result

    Wait for the saved state. For deletion, read the confirmation and use it only for a genuinely retired entry. Recheck the list and related evidence.

Confirm success: The service shows the intended monitoring state.

Stop and check: Disabling monitoring does not fix the service; it changes visibility.

Troubleshooting

Control unavailable

Check both module entitlement and role; do not bypass the restriction.

Terms

Daily extraction pipeline

Follow the daily IDC/DigiPay extraction through validation and file readiness.

Access: Daily extraction access; triggering runs and changing sources have separate permissions.

Navigate to /trustlink?tab=pipeline

Check today’s extraction

Before you begin: Know the required business date and enabled sources.

  1. Read the run identity

    Open Trustlink and Pipeline. Check date, status, selected run and source route. Confirm whether today’s export already exists.

  2. Follow each stage

    Read IDC Ingest, DigiPay Ingest, Transformation, Validation, File Save and Download. Inspect failed/skipped stages and row counts; an intentionally disabled source is not a successful ingestion.

  3. Download the ready file

    Use Download Export only when the file is present. Confirm the filename/date and record counts before onward delivery through your approved process.

Confirm success: You can show which inputs ran and which export is ready.

Stop and check: A completed extraction or local download is not proof that an external recipient received the file.

Troubleshooting

Run failed or file absent

Inspect the failing stage and history. Ask an authorized operator to recover the run rather than repeatedly triggering new runs.

Terms

Pipeline: The ordered stages that turn source data into an export.

Extraction run history

Inspect past runs and retrieve the correct retained export.

Access: Run history access; file deletion remains restricted by role and run eligibility.

Navigate to /trustlink?tab=history

Inspect or download a historical run

Before you begin: Know the date/run you need.

  1. Select the run

    Open History and narrow the period/search using the available controls. Open the run inspector to read stage outcomes, timestamps, row counts and errors.

  2. Retrieve the artifact

    Use Download only if the run has a file. Match filename and business date to your request. Missing files are different from missing run history.

Confirm success: The downloaded file belongs to the selected recorded run.

Stop and check: Do not substitute today’s file for a missing historical export.

Remove an eligible saved export

Before you begin: Have authorization to remove that artifact.

  1. Review the eligible file

    Use the delete-file control only where offered. Read the confirmation for the selected run; file removal is not a rerun.

  2. Confirm the outcome

    After confirmation, verify the file is unavailable and inspect the retained run record.

Confirm success: The artifact availability and run history reflect the deletion.

Stop and check: Do not delete a file still needed for delivery, reconciliation or retention.

Troubleshooting

Download unavailable

Check file presence in the inspector; request the approved recovery path if it was removed.

Terms

Manual extraction and overwrite

Start a controlled extraction or replace today’s export when justified.

Access: Manual extraction access plus the operation’s role restrictions.

Navigate to /trustlink?tab=pipeline

Run an extraction

Before you begin: Verify today’s state and that source configuration is correct.

  1. Inspect before triggering

    Check whether a run is active or today’s export already exists. If ready, download it instead of creating a duplicate.

  2. Run and follow

    Choose Run Extraction (or Trigger First Run). Wait for scheduling, then follow Pipeline through completion and file readiness.

Confirm success: The new run has a terminal status and a verified artifact.

Stop and check: A scheduling response means accepted, not completed.

Overwrite today’s export

Before you begin: Have a valid reason and approval to replace the existing output.

  1. Review what will change

    Inspect today’s existing export and affected delivery process. Choose the overwrite action and read its warning.

  2. Confirm deliberately

    Accept only if replacement is intended. Follow the resulting run and verify the new file/date/counts before distributing it.

Confirm success: The replacement export is checked and the run history explains the operation.

Stop and check: Do not overwrite simply to troubleshoot a download or while another operator is distributing the previous artifact.

Troubleshooting

Already exists

Download the current export, or use the explicit overwrite workflow if a replacement is authorized.

Terms

Extraction source configuration

Choose the data sources used by the next extraction.

Access: Source configuration access and Admin role.

Navigate to /trustlink?tab=pipeline

Change IDC/DigiPay ingestion

Before you begin: Know the approved extraction route.

  1. Inspect the current route

    Read the IDC and DigiPay ingest controls and the current run’s evidence.

  2. Change the next route

    Toggle the intended source. At least one source must stay enabled. Wait for the saved “Next extraction route” message.

  3. Verify the next run

    Inspect its stage outcomes and counts. The toggle does not retroactively rewrite an earlier run or artifact.

Confirm success: The next extraction uses the intended enabled inputs.

Stop and check: Do not disable a source to hide a failed ingestion without business approval.

Troubleshooting

Both sources cannot be disabled

Keep the required source enabled; the form deliberately rejects an empty route.

Terms

RTGS recovery and automation

Assess RTGS cases and request governed regeneration with a reason and evidence.

Access: RTGS access; recovery uses configured operator authority, policy changes require Admin.

Navigate to /trustlink?tab=rtgs

Investigate RTGS cases

Before you begin: Know the transaction reference or age lane.

  1. Run/read the assessment

    Open RTGS. Refresh the database assessment and inspect cases by age/status. Read the case evidence and eligibility before selecting it.

  2. Inspect custody

    Read the relevant run/action result and source state. Distinguish a regeneration request from final payment processing.

Confirm success: You have fresh evidence for each intended recovery.

Stop and check: A case’s age alone is not sufficient authority to regenerate it.

Regenerate selected cases

Before you begin: Resolve the underlying issue and obtain the operational reference.

  1. Select eligible cases

    Select the exact transaction IDs. Review older-than-96-hour cases carefully; the request carries that acknowledgement for selected aged cases.

  2. Provide a reason and submit

    Enter a meaningful reason/change reference of at least eight characters. Submit the regeneration action once. Read per-case outcomes, including partial failure.

  3. Reassess

    Run the database assessment again to see updated queue state and inspect action history.

Confirm success: Each request has a recorded outcome and refreshed source evidence.

Stop and check: Do not repeat a request blindly after a timeout or assume regeneration proves payment settlement.

Maintain automated recovery and cadence

Before you begin: Have Admin authority for policy and approved schedule intent.

  1. Review current controls

    Inspect automatic five-day regeneration and the returned active schedule. Read the current cadence and enabled state.

  2. Change and verify

    Toggle the authorized policy or select the offered 30/60-minute cadence. Wait for saved confirmation and re-read the active schedule/action history.

Confirm success: The policy and active schedule reflect the approved change.

Stop and check: If the runtime has not returned a schedule, the displayed selection alone does not configure automation.

Troubleshooting

Some cases failed

Review each outcome and fresh assessment before deciding on another request.

Terms

Regeneration: Recreates/requeues the eligible processing request; it is not evidence of settlement.

Fabric overview

Read the fabric’s current posture and move into the correct investigation.

Access: Fabric overview access. Each Nexus workspace also has its own entitlement.

Navigate to /nexus

Orient yourself in Nexus

Before you begin: Know the environment or affected business journey.

  1. Check freshness and scope

    Open Nexus. Read the overview and refresh state. Use search to locate incidents, services, clusters, flows or dependencies.

  2. Choose the right workspace

    Use Incidents for current/unresolved cases, Services for runtime evidence and controls, and Clusters/Flows/Dependencies for relationships. Linked Stats and Network Sentinel consoles require their own access.

  3. Separate facts from inference

    Read source timestamps and evidence before acting on a root-cause suggestion. An unavailable source is not healthy and a likely cause is not a confirmed verdict.

Confirm success: You know which workspace holds the evidence and which service/incident to inspect.

Stop and check: Do not execute controls from a summary alone. Open the detailed evidence and relevant procedure.

Troubleshooting

Workspace missing

Ask the section administrator to check that specific module; the overview does not grant all Nexus operations.

Terms

Fabric: The catalog of services, their relationships and operational evidence.

Correlation: Combining signals to propose a shared incident or cause.

Incident investigation

Investigate impact, gather evidence, coordinate response and record a verified outcome.

Access: Incident investigation access; diagnostics, tasks, verdicts and notification settings remain role-gated.

Navigate to /nexus?workspace=incidents

Investigate an incident

Before you begin: Identify the affected journey/service and incident time.

  1. Choose a case

    In Incidents, use All unresolved, Active now, Shift pulse, Last 24h or Older. Open Incident Command View. Restored cases can still await an operator verdict.

  2. Read the evidence

    Review Overview, Topology and Evidence. Compare suspected root, confidence, affected services, timeline and business-flow scope. Inspect original evidence when a mapped link is available.

  3. Request assistance

    Use Request Diagnostics if allowed, then inspect the resulting Actions/evidence. Create Response Task for owned follow-up. SOP Copilot can explain/cite procedures; verify the cited version and prerequisites.

Confirm success: The response is based on dated evidence, with assigned follow-up where needed.

Stop and check: Confidence is a hypothesis score, not certainty. Missing deep-link mapping should be corrected in the catalog, not guessed.

Record an operator verdict

Before you begin: Have verified the cause and whether the action worked.

  1. Review the restored state

    Compare current signal and the incident end time. Confirm whether impact ended and identify remaining work.

  2. Record the outcome

    Open Outcome. Supply the supported verdict, actual root/cause, action result and explanation required by the form. Submit once and confirm the recorded learning/closure state.

Confirm success: The incident carries an attributable human outcome, not just automatic recovery.

Stop and check: Do not confirm a root cause merely because it was Nexus’s top candidate.

Configure incident notification delivery

Before you begin: Have Admin authority and an approved recipient/channel scope.

  1. Open Notification Mesh

    Choose Configure. Review active-shift recipient scope, channels, extra email recipients and last delivery/queue state.

  2. Save and inspect delivery

    Set the approved controls, save, then inspect subsequent delivery status and failures. Extra recipients must be intentional.

Confirm success: The mesh shows the saved scope and evidence of delivery attempts.

Stop and check: In-app or email delivery status does not prove a person read the message. Desktop browser alerts require supported HTTPS permission.

Troubleshooting

Diagnostics/action fails

Read the returned error and Actions record; do not repeat disruptive commands.

No evidence link

Open the correct service contract and have its Network Sentinel mapping verified.

Terms

Awaiting verdict: Impact may have ended, but human investigation closure is still pending.

Blast radius: The services or journeys inferred to be affected.

Service catalog and controls

Inspect a service’s live evidence and manage its governed contract and controls.

Access: Service catalog access; catalog changes require Admin, runtime actions require configured authority and successful gates.

Navigate to /nexus?workspace=services

Investigate a service

Before you begin: Select the correct service and environment.

  1. Open Live Operations

    Read active impact, runtime agent, Network Sentinel, host posture and heartbeat. Check timestamps; no signal/unknown is not healthy.

  2. Inspect signals and logs

    Open the signal explorer and log-tail/evidence controls offered by the contract. Set the relevant scope and refresh. Compare runtime observations with external probes and incident history.

Confirm success: You can identify the source and age of each observation.

Stop and check: Log excerpts can contain sensitive operational data; share only the necessary evidence.

Create or update a service contract

Before you begin: Have the stable identity, owner, environment, bindings and approved endpoints.

  1. Open Contract Configuration

    Create a service or edit the selected contract. Set its identity/type, ownership, agent/network bindings, observation settings and certification stage.

  2. Set valid control routes

    Supply only approved extraction, formatting, shipping, diagnostics and control endpoints exposed by the editor. Review timeout/safety settings and associated cluster routing.

  3. Save and validate

    Save and inspect fresh evidence from the service. Delete only retired contracts after reviewing the impact and confirmation. A saved endpoint is not a proven working endpoint.

Confirm success: The persisted contract and live evidence describe the intended service.

Stop and check: Do not promote certification or enable control merely to make a button available.

Start, stop or restart a service

Before you begin: Have change authority, verified service identity, current evidence and a justified action.

  1. Open the Service Control Gate

    From the service or incident choose Service Control. Read eligibility, readiness, allowlisted action and current runtime state. Request diagnostics first when required.

  2. Request and verify the challenge

    Choose the intended action and provide the required reason. Request the OTP challenge. Check the action/service again before entering the issued one-time code.

  3. Follow the result

    Submit once and inspect command outcome and fresh service state. If blocked, expired or uncertain, read the reason and reconcile before a new request.

Confirm success: A command has an attributable result, supported by refreshed runtime evidence.

Stop and check: Never treat STOP/RESTART as a harmless probe or reuse an expired challenge.

Troubleshooting

Control blocked

Read the gate: readiness, certification, allowlist, cooldown or missing evidence must be resolved legitimately.

Stale heartbeat

Check the agent and telemetry route before treating the runtime state as current.

Terms

Contract: The saved identity, bindings and allowed operations for one service.

OTP: A one-time code that confirms the requested controlled action.

Agent monitoring

Inspect the runtime agents that report service evidence and carry allowed commands.

Access: Agent monitoring access; onboarding credentials and catalog edits have separate controls.

Navigate to /nexus?workspace=agents

Investigate an agent

Before you begin: Know the host/agent expected to report the service.

  1. Open the agent
